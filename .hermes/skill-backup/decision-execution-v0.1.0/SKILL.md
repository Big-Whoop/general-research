# Decision Execution Skill

This skill governs what happens AFTER a `decision-narrowing` loop has terminated: the implementation runs under the loop's artifacts, not beside them. It is stage 3 of the decision pipeline — `deep-research` (stage 1) builds the options-complete corpus, `decision-narrowing` (stage 2) narrows it to one path under user constraints and decisions, and this skill (stage 3) carries that path into implementation while keeping the artifacts the binding rulebook. It defines the precedence stack for conflicts, the formal mechanism for revising decisions when implementation evidence contradicts them, the archive mode of `STATE.md`, and the reading protocol that keeps an executing agent out of the research corpus unless it genuinely needs it. It does not decide anything new (that is `decision-narrowing`) and does not plan (that is `plan`) — it enforces how decisions travel from paper into code and survive contact with reality. It depends on the loop artifacts and the corpus existing in the repo; without them there is nothing to execute.

## When to Use

Load this skill when you start an implementation session whose target was chosen by a completed `decision-narrowing` loop — typically the first session after the loop's final DECISION entry, or any later session or subagent dispatched to work inside that implementation. Load it again at the moment you hit the first conflict between what you are about to build and what the artifacts say, before writing any code or touching any infrastructure. Do NOT use it while the narrowing loop is still running (that skill owns the loop, including its own SUPERSEDED mechanics), for work that no decision loop ever governed (plain feature work has no artifact set to enforce), or to make new architectural decisions — if implementation evidence shows that the design space itself must move, the matter returns to `decision-narrowing` or to the user, and this skill only records what was decided, never decides it.

## Prerequisites

The loop must be closed: `DECISIONS.md` holds the terminating decision (explicit user pick or user-confirmed sole survivor), and the final `STATE.md` shows ONE_PATH or TRIVIAL_CHOICE with the termination proof. The research corpus from stage 1 is persisted in the repo inside the topic directory (`.hermes/decision/<topic>/research/`) with its manifest README, so that a revision can always re-open the exact sources a decision was based on. An implementation plan exists (from `plan` or the loop's Close step). The three loop artifacts are git-tracked, because the executor's only world-model is what is committed — uncommitted artifacts are artifacts that do not exist for the next session. The topic directory layout is in place: `.hermes/decision/<topic>/` containing `README.md`, `CONSTRAINTS.md`, `DECISIONS.md`, `STATE-final.md`, the plan, and `research/`. If the artifacts still sit loose in the repo root, the corpus is still in a generic research dir, or the final state is not frozen, complete the migration described in the procedure BEFORE doing any implementation work.

## Procedure

1. **Enter through the artifacts, in this fixed order, at the right reading level.** The topic carries four reading levels, and you descend only as far as you must: **L0 (always)** — the topic `README.md` (what is decided, what is open, the precedence stack, the provenance chain in one screen), then `CONSTRAINTS.md`, then `DECISIONS.md` (non-superseded entries only — superseded entries are read only to understand why a successor exists), then the plan. **L1 (on conflict or "why")** — when L0 leaves a question you cannot resolve (why did path X die? what has already changed during implementation?): `STATE-final.md` (rounds, eliminations, termination proof) and `REVISIONS.md`, plus the manifest line in `research/README.md` for the affected file — the manifest tells you which research file carries which claim without you opening it. **L2 (only to revise or re-validate)** — individual research files, one at a time, only the sections the manifest points at, and only when a formal revision (step 5) or a plan change touching a load-bearing claim requires the underlying evidence. Never bulk-read the corpus: the corpus is the option matrix the loop already consumed, and re-reading it wholesale is how an executor drifts back into re-deciding. Use `read_file` per file and `search_files` to locate the topic directory before assuming a layout. Completion: you can state, for the specific task you are about to do, which constraints and which non-superseded decisions it sits under, by id — and if you opened anything at L1/L2, you can name the exact question that justified the descent.

2. **Freeze the decision state before building.** Rename the final `STATE.md` to `STATE-final.md` so that its filename declares it closed, and record in the topic `README.md` that the loop terminated on round N with path X. From this point on no session rewrites, re-runs, or appends to `STATE-final.md` — it is evidence of how the decision came about, not a working document. If you are the session that just closed the loop, do this as the last act of the loop's Close step, not the first act of the next session. Completion: `STATE-final.md` exists, no writable `STATE.md` remains in the topic directory, and `git status` shows the migration staged.

3. **Write the topic `README.md`** as the single entry point for future readers, in four blocks: (a) the terminating decision set (ids only, one line each); (b) the list of deferred live items (the loop's OQ/US-class items) and where they are tracked (the plan); (c) the precedence stack in its exact order — repo ground rules (e.g. `AGENTS.md`) → CONSTRAINTS → DECISIONS → plan; (d) **Provenance** — the pipeline chain with versions and dates: `deep-research` (version, research dates, corpus location `research/` with its manifest), `decision-narrowing` (version, loop dates, rounds 1–N), `decision-execution` (version, from which date), plus the note that every C#/D# entry carries a Source field and the research manifest maps files → axes → C#/D#, so the full derivation chain from raw source to running code is reconstructable from the directory alone. Keep it under one screen; it is an index, not a summary. Completion: a reader who has never seen this topic can answer, from the README alone, what was decided, what is still open, which file wins a conflict, and how everything here came to exist.

4. **Enforce the precedence stack in every conflict you meet.** A higher tier always wins, and the winning tier is never edited — the losing artifact is corrected to match the higher one. Implementation contradicts plan: fix the plan, not the implementation. A decision appears to contradict a constraint: the constraint wins, and the decision is retired by a formal revision (step 5), never routed around, never "worked around with a flag". A constraint appears to contradict a repo ground rule: stop and surface it to the user — a constraint the ground rules forbid was never valid, and finding it is a defect in the loop's output, not in your implementation. You never, in any of these cases, edit `CONSTRAINTS.md` or `DECISIONS.md` entries in place: both files stay append-only for the entire life of the topic, not just during the loop. Completion: the conflict is resolved in the higher tier's favor, the lower-tier artifact carries a visible correction, and no file below the winning tier was silently changed to paper over the conflict.

5. **Revise a decision only through a formal revision entry.** When live evidence (a failed test, a measurement, a constraint conflict discovered on-target) shows that a high-altitude decision cannot stand, file a NEW entry in `DECISIONS.md` — never touch the old one — carrying: the new entry's id continuing the sequence (D6 after D5, never reusing numbers), the explicit status "revised during implementation", the exact id it supersedes, the old entry marked `SUPERSEDED by D#` (a single appended marker line inside the old entry — append-only still holds; where the old entry bundles several sub-decisions, scope the marker to the superseded sub-part only and state explicitly which parts remain in force — a **partial supersede** — rather than retiring the whole entry), the evidence that forced the revision, the new rationale, and source (test name / measurement / conflict with which constraint). Before filing, re-validate the new decision against the ENTIRE current constraint set, entry by entry: the old decision was validated against that set, and the new one must satisfy it too — and where the original decision's Rationale cited a research file, re-open that file at L2 (step 1) and check whether the new decision contradicts the underlying evidence or merely a misreading of it. If the new decision violates any constraint, the problem is the constraint, not the decision — stop, surface the conflict to the user (step 6), and file nothing. A revision is the expected feedback channel of the decision phase, not a failure of it: the paper loop could only decide as much as the corpus knew, and on-target tests are precisely where evidence it did not have arrives. Completion: the new entry exists with all fields, the old entry is marked superseded (not deleted, not edited beyond the marker), the re-validation is written out entry by entry (including the ones that passed — a revision that only cites the passing constraints is a check you did not perform), and the next session reconstructs the full chain — why D2 was filed, why D7 superseded it, what evidence stood behind each move — from the files alone.

6. **Return constraint-level changes to the user.** An implementer never files, supersedes, or amends a constraint. If step 5's re-validation, or any other finding, shows that a constraint itself must move — it was drawn wrong, reality is outside the design space it carved, or two constraints now contradict each other — present to the user the exact conflict, the evidence, and your recommended resolution, and wait. Only the user's answer, filed as a new superseding constraint by the user-authorized session, changes `CONSTRAINTS.md`. Completion: the constraint set is unchanged from before you started, and either your implementation conforms to it or the user has explicitly moved it.

7. **Treat the plan as the least stable artifact, with a revision trail.** The plan is a snapshot of how the chosen architecture looked most buildable at one moment; reshape it freely during implementation as long as it satisfies the current constraint and decision sets. Every plan change beyond pure implementation detail — a re-sequenced phase, a dropped task, a newly appearing component — gets a one-line note appended to `REVISIONS.md` in the topic directory (append-only, same discipline as the source files) naming what changed, why, and which decision/constraint the new shape still satisfies. Small detail-level churn (variable names, task wording) needs no note; the line is drawn at "would a re-reading session plan the same sequence differently". Completion: the plan and `REVISIONS.md` together let a re-reading session distinguish intentional re-planning from drift.

8. **Record deferred live items the moment they are resolved — during the session, not at phase end.** Two resolution paths: a hands-on question the user delegated to implementation gets answered by the user mid-build (ask one at a time, with your recommendation; the answer is their pick); an on-target question gets resolved by a live test/measurement. Either way, file the answer the moment it lands: (a) the plan's OQ table / task notes — status line with the chosen option and where it is implemented; (b) a one-line REVISIONS.md note if the answer changes the plan's shape or sequence (step 7's bar); (c) the topic README's open-items list, so L0 readers see it closed. Commit the three as one small commit — an answer that lives only in chat is lost for the next session (the same loss mode as the chat-only pitfall below). A hands-on user answer stays an implementation-level plan record UNLESS it changes what gets built — that instant is step 9's promotion trigger, not a duplicate OQ note.

9. **Promote on-target decisions to formal entries the moment they become load-bearing.** Deferred live items (the OQ/US-class questions the loop parked for implementation) stay in the plan until they are decided on-target — that is normal, not debt. The instant one of them has architectural consequences (it changes what gets built, not just how), it is filed as a DECISIONS.md entry with source "on-target test <name>, <date>" — never parked only in a commit message, a todo list, or the plan's task notes. Conversely, a live test that only confirms the paper decision needs no entry; note the result in the plan's task and move on. Completion: every architectural fork resolved on-target is traceable to a DECISIONS.md entry with evidence, and the plan's deferred-items list matches the entries filed so far.

10. **Handle a user's "let's re-plan / move X to the end" request as a classification, then a dependency pass.** First classify each element of the request against the stack before touching the plan: (a) pure re-sequencing of phases with no change in what gets built = plan change + one REVISIONS line (step 7); (b) a change in WHAT gets built (a new component such as a secrets platform, a different node for a workload) = DECISIONS entry (step 9) — and if that component is not in the corpus, a small docs-first research note into `research/` (manifest row) BEFORE the D# entry, never a D# from trained knowledge alone; (c) anything that moves a constraint = user (step 6). Say the classification out loud to the user in one line so they see which tier moves. Then the dependency pass: a phase rarely moves alone — find its counterpart (an edge host and its tunnel peer, a node Day-0 and the workloads pinned to it) and move the pair; re-read every later phase for text that assumes the old order ("all N hosts", "after phase X") and list those lines as edits; and ask the user for placement/ownership facts you cannot derive from the repo (which host a workload belongs on, whether a target machine is a reinstall of a live box or a spare) ONE question at a time with a recommendation — the user holds hardware pairings and usage facts the repo does not. For migrations of existing services, present the per-item template (recon read-only → manifests → data/secrets → cut-over with the old instance kept as rollback) before the phase table, so the user can object to the shape before the sequence. When a workload is pinned to a node that does not exist yet, pull that node's Day-0 ahead of the workload's migration rather than landing it elsewhere first — land-then-move is churn, and a blue-green move of the agent's own runtime needs its target node already in the deploy loop. Completion: every moved element is tagged with its tier, every coupled phase moved with it, and the open user questions are listed — none answered by assumption.

11. **When a quota, cap, or license tier threatens to eliminate an option, define the counted unit before accepting the elimination.** Users (and research notes) count the wrong thing — hosts instead of accounts, nodes instead of identities, pods instead of seats. State in one line what the vendor actually counts and recount against the real design (one shared cluster identity, not one per host); only if the honest count still breaks the cap does the option die. Record the corrected count in the D# Rationale so the next reader does not re-run the wrong arithmetic. The same discipline applies to "free vs paid" feature splits: name the paid features the user gives up in the D# so the acceptance is explicit, not implied.

12. **Treat a recon card's "open questions for the user" as step-8 items: read them to the user numbered, one recommendation each, and file every answer in the plan task the same session as a numbered A# list that later cards cite.** Also fold the recon's corrections of your own seeded facts into the plan (and fix every downstream task that inherited the wrong fact — source host, data path, consumer list); a seeded fact that came from memory or a skill rather than from the target is a premise to verify, so mark such seeds "to confirm" in the card body instead of stating them as fact.

13. **Before planning the first user-facing cluster service, settle naming and name resolution as their own decision.** A service exposed by hostname needs (a) a zone that is distinct from the host-identity zone and (b) a mechanism that creates records without a human — otherwise the first verify card fails on "name does not resolve" and every later workload is renamed once the zone arrives. When the user asks for "managed DNS", classify it as a what-gets-built change (D# with a short docs-first note), insert it as a phase BEFORE the workloads, and rename anything already routed under the wrong zone while no account or consumer exists yet. Record the one unavoidable manual step (the router's zone forward) in the re-validation as an accepted residual of the self-healing constraint, same class as DHCP reservations.

14. **A user's operating policy ("updates never automatic", "backup is non-negotiable", report cadence, rollback rule) is a CONSTRAINT, not a decision or a plan note** — file it in `CONSTRAINTS.md` verbatim-in-intent the session it is stated (numbered points, with the user's reasoning as rationale), and keep the brainstormed HOW (tools, schedule mechanics, storage layout) as plan-level text marked "decision pending" until a docs-first note feeds the D# entry. Mixing the two produces a decision the user cannot later distinguish from their own rule. When such a policy depends on another capability (rollback needs a snapshot; a snapshot needs the backup), order the phases by that dependency and say so in the constraint's rationale.

15. **When implementation evidence shows a decided storage/transport path is incorrect (not merely slow) for a workload already in flight, stop that card before cutover and insert the fix phase in front of it** — even mid-chain, even with a copy already running. A move that lands on an unworkable substrate is churn twice (move, then re-move); a parked copy is cheap. File the new D# with partial-supersede markers on every earlier D# whose storage sub-part it overrides, and re-gate the parked card behind the fix chain.

16. **Before asking the user to decide from a research note, diff the note against every LATER decision.** A note written for an earlier design (e.g. backup "on the build host via NFS") can be silently invalidated by a later D# (state moved to iSCSI, visible only on the consuming node). Name the conflict in one line, then ask the question with the option that matches the newer decision recommended first. Why: a user who picks from the stale note re-decides a settled point, and that costs a revision later.

17. **"Does option X violate a security constraint?" — answer by walking the constraint list, then name the residual.** Go through every C# that touches trust boundaries, one line each: whether X creates a new path across the boundary (inbound port, tunnel prefix, new egress), or no path at all. Then name the risk X adds even when no constraint is broken. Typical example: a credential that now also lives in a second place, such as a DNS-API token in the cluster for ACME dns-01. Make the matching requirement part of the D# (least-privilege scope, separate credentials per trust zone). Why: "no constraint violated" without the residual hides exactly the trade-off the user is asking about.

18. **User answers that cannot be filed yet still get filed somewhere durable that same turn.** If DECISIONS/REVISIONS edits must wait (open worker docs-PRs would conflict), write the answers into the body of a queued docs card. Gate that card behind the open PRs, or add the answers as a comment on the card that will file them. Tell the user where they are parked. Why: answers held only in chat are lost at compaction or handover. That is the same loss mode as step 8.

19. **Phase re-ordering by the user that exposes an unplanned scope gap:** when a pulled-forward phase leaves a capability undefined (e.g. certificates planned only at the edge, LAN stays plain HTTP), ask ONE A/B question that names the gap, recommend first, and say whether the answer needs a new D#. Start the always-allowed read-only recon of the phase's target (Gate 3) in parallel, as its own card. Recon never needs the answer.

20. **A user-proposed batch of new constraints ("let's check and update some constraints"):** first map each point against the existing C# list. A point an existing constraint already covers becomes an appended addendum to that C#, not a duplicate; an exception to an existing C# is a new C# plus a one-line addendum on the old one. Then go through the open points ONE question per turn, recommendation first: resolve ambiguous terms (e.g. "the gateway" = edge or internal), propose the class-level carve-outs the rule needs to be workable (machine-to-machine access, break-glass admin, transition period for lockout-prone hardening), and say where a literal reading is infeasible (e.g. port stealthing on a port that must stay public). When the user names a client the rule could break (a native app, a CLI), check that product's own docs for support (e.g. OIDC/PKCE native sign-in) before granting an exception; cite the doc page and mark undocumented parts "to live-test". After the last answer, show the full C# table once, then file everything through one docs card (constraints appended, plan + REVISIONS, research stub for any decision the constraints now require). Why: constraint wording is the user's alone, and a constraint filed with an unresolved ambiguity forks into two readings later.

21. **"Does this match best practice?" about an already-decided design: answer honestly, including where you would now decide differently.** Separate what matches common practice, what deviates on purpose (traced to a C#), and what you would change, with the mechanism of the risk (e.g. TLS terminated on the least-trusted host exposes every session in plaintext to a root compromise). Say it is from knowledge, not fresh research. Then propose a deep-research card that compares the options, writes a revision draft for the affected D# (options table, recommendation, constraint check entry by entry, plan-order impact), and blocks for the user. Put the dependent plan/implementation PR on hold in the same turn with a comment on its card. Why: a flaw found after a decision is cheapest to fix before implementation starts. A silent "yes, best practice" ships it. After the user picks: (a) record the pick on the research card so the revision (new D#, partial-supersede marker) lands in the same PR; (b) check every constraint whose wording assumed the old design (e.g. "edge: TLS ≥ 1.2, rate limit" when the edge no longer decrypts). Ask the user once whether it may be met jointly by the new components. File the yes as an appended addendum to that C#, never as a rewrite; (c) name credentials or artefacts the revision makes obsolete (e.g. a token now unused) and ask the user to revoke them right away; (d) lift the hold and have the held plan PR revised in place against the new D#.

22. **Recurring manual chores: recommend "event-driven only", not a schedule.** This user rejects periodic human tasks (token renewal, yearly key rotation, calendar reminders to re-issue a credential), because nobody remembers them and an expired credential then breaks a renewal loop silently. Default recommendation for credentials and keys: unlimited validity (if the provider allows it) with least-privilege scope, separate credentials per trust zone, and revoke+replace only on suspected leak. Name any provider-side auto-expiry that still applies (e.g. a token disabled after a year of NON-use) and say why normal operation keeps it alive. A dated reminder is fine only for a one-off step tied to a plan stage, worded with its precondition.

23. **Long sign-off rounds: batch only the trivial points.** Ask substantive questions one per turn. Two or three yes/no hardening details (port closed, ICMP off, default port) may go in one turn as a numbered list, "reject any single one". The user answers per number and may change one (e.g. "80 only for a redirect"). Fold such a change into every affected plan section (firewall rules, ruleset, provider steps), not just the decisions list.

24. **Starting implementation from a HANDOFF document: run the sign-off as a numbered question round, one question per turn, recommendation first, and classify each answer's tier out loud.** Order the questions by dependency: (1) where the new work sits in the current execution order (plan re-sequencing → one REVISIONS line), (2) where a separate codebase lives (this user wants: private repo, own Hermes desktop project, own Kanban board, parallel development), (3) agent access to any new target (read-only sudo whitelist first, write rights after plan sign-off), then the handoff's open-items list. Run the always-allowed read-only recon as soon as access exists and fold the facts into the next question (closes handoff items without a card). Say which answers become a C# (operating policy), which a plan A# (layout, version pin), and which need no entry. "Missing from the corpus" means *no researched evidence*, not *forbidden* — if the user picks such a version anyway, verify the pin docs-first (release page, checksum) and file a short research note so the D# has a source. When the user adds "plus X" and X is already in the proposal, ask which variant they mean (e.g. SSH *through* the wrapper vs. native SSH with the agent's own key) instead of assuming. Deliver scripts for the user from `/opt/data/downloads/` — the desktop preview rejects repo paths outside the managed read boundary. Do not propose guardrails the user did not ask for on his own hardware (VM size caps, quotas, concurrency limits) — he sizes test workloads himself and monitors resources manually; offer only fail-safe defaults (no overcommit → oversize request stays Pending). Do not pull a risky-but-in-scope sub-step (e.g. the GPU plugin) out of its phase "to reduce risk" — he prefers finishing the phase in one go; keep it as its own card inside the phase instead. End the round in one turn with: docs PR (plan + C#/addenda + README/REVISIONS/manifest + research note), the bootstrap of the separate codebase (private repo with README/AGENTS.md, Kanban board, desktop project — switch the session back afterwards), and an OFFER of the first two cards (recon + scaffold) — never create cards unasked. When the no-infra track (docs, separate codebase, recon) is finished, OFFER the cluster-touching chain and expect the user to pull it ahead of the remaining phases the moment the milestone that justified the ordering has passed (e.g. an edge hardening step proven live) — classify that as plan re-sequencing (one REVISIONS line naming why the pulled-ahead track does not collide with the skipped phases and which single touchpoint waits, e.g. TLS on a route), ask for the downtime window in the same question, and seed the whole chain at once rather than card by card. Before the scaffold card exists, ask the runtime and framework versions as their own question (this user wants the newest LTS runtime and the latest stable GA framework unless a D# pins otherwise) — a D# that names only the framework ("Spring Boot WebFlux") is not a version pin, and a correction after the scaffold worker started costs comments on the card, a docs fix in the new repo, and a plan line in the next docs PR.

25. **Secrets policy (this user; file as a constraint): secrets are generated by the provisioner path, never typed by hand and never chosen by the agent; the value is not returned to the agent (name/path/status only).** User passwords (interactive logins): 16 chars from `A-Z a-z 0-9 - _` (`openssl rand -base64 18 | tr '+/' '-_' | cut -c1-16`); hex fallback only if the tool cannot produce that alphabet. Machine secrets: whatever is best practice for the consumer. Storage Infisical, consumption via ESO, humans read in the Infisical UI. Infisical's create API takes a client-supplied value (no server-side generation except dynamic secrets), so "generate without the agent seeing it" is a generate mode in the provisioner script, not an Infisical feature. Machine-to-machine APIs in the LAN use per-consumer bearer tokens from this path; the SSO constraint covers human logins only — state that reading explicitly as a constraint addendum, never as a silent exception.

26. **A D# that names an exact patch version is a pin on the *line*, not a promise the distro ships that patch.** When the recon shows the locked package source supplies a different patch (e.g. nixpkgs at the flake lock carries 1.36.4 where the D# says 1.36.2), ask the user ONE question with "take the distro's patch" recommended first — forcing the older patch means an overlay with its own source hash, i.e. unpinned-hash maintenance for a version that is strictly older. File the answer as a new D# with a *partial* supersede marker scoped to the version sub-part (the upgrade decision and its rationale remain in force), and have the card that found it file it in the same docs PR — a version pin that lives only in the chat gets re-discovered by the deploy card.

27. **Agent access to a new target host (non-fleet box the user owns) is staged in two sudoers drop-ins, both delivered as scripts the user runs** — mechanics in `references/agent-host-access.md`. Read-only whitelist first (unblocks recon the same turn), setup rights second, derived from the recon card's collected command list and kept after setup (day-2, no churn).

28. **Before seeding the scaffold card of a new service, ask the user the "framework defaults that are not in the D#" as ONE batched trivial-points turn (step 23 shape):** runtime version, framework version, and the operator-facing conveniences the user will expect on day one (API docs UI with a working Authorize button behind the same auth, health endpoint unauthenticated). A D# like "Spring Boot WebFlux" fixes neither of these, and the user asks for the missing convenience after the scaffold merged — then it costs a comment on a running card instead of a line in the card body. Keep auth on the docs UI (the SSO/token constraint has no exception for documentation pages); declare the security scheme in the OpenAPI so the UI is usable with a token.

## Pitfalls

The quiet workaround: the code (or the plan) bends to "get the job done" while a decision stays formally in force, so the artifacts and the build quietly diverge and a re-reading session implements the dead version. The test is structural — if any non-superseded DECISIONS.md entry does not describe what the build actually does, you are in this pitfall and must file the revision (step 5) before continuing. The second is the in-place edit: fixing the wording of an old constraint or decision "because it was never really meant that way" destroys the audit trail; a changed meaning is a new superseding entry, always. The third is deleting or renumbering superseded ids — cross-references in the corpus, the plan, and `STATE-final.md` point at those numbers forever, and a renumbered D# silently points at the wrong decision for every later reader. The fourth is treating the re-validation in step 5 as a formality: a new decision that violates a constraint added three rounds ago is exactly the failure mode the loop's last-round-only pitfall warns about, replayed one phase later. The fifth is rewriting `STATE-final.md` with implementation progress — it is frozen evidence, and progress belongs in `REVISIONS.md` and the plan. The sixth is letting live-test results live only in chat or commit messages; untracked decisions do not exist for the next session and the same fork gets re-decided, sometimes differently. The seventh is an implementer filing a constraint change because the implementation is "clearly" incompatible — that is step 6's user decision, full stop, and a self-filed constraint amendment is a process violation the next reader cannot distinguish from a user one. The eighth is batch-recording deferred answers at phase end: several OQ/US resolutions piling up in chat and landing as one retroactive plan edit — each one should have been filed the session it was decided (step 8), because a later session re-reading L0 in the meantime sees the item as open and may re-decide it. The ninth is bulk-reading the research corpus out of caution: the manifest exists precisely so you can verify a claim against one file's one section; re-reading the whole corpus is drift back into stage 2, and it is also how a stale or superseded research file (the loop already marked some lines STALE in `STATE-final.md`) resurrects a dead path. The tenth is writing a plan task from an inferred live-state premise: a thin host config does not mean the host is uninstalled — before adding or rewording a task that depends on what is running (installed? deployed? in the loop?), check the repo's own state notes (flake/host comments, `git log -- hosts/<h>`, deploy scripts) and say which you checked; a wrong premise committed to the plan costs a correction entry and the user's trust. The eleventh is starting a phase without scanning for irreversible parameters: when planning a phase, list the values that cannot change after first start (cluster/service CIDRs, disk layout, key identities, cluster names), and where the corpus or plan carries conflicting values for one, surface it to the user as an explicit question with a recommendation BEFORE the card runs, then file the answer as a DECISIONS entry (step 9 — it changes what gets built) and fix every plan reference.

## Cleanup passes (user-requested "look around / tidy up")
