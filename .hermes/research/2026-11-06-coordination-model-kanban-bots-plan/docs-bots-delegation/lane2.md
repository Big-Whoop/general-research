## B. Findings (claim · source · quote · tier)

### (a) Bot Mode

1. **A Bot is a profile; Bot Mode adds no execution primitive.** — https://hermes-agent.nousresearch.com/docs/user-guide/bot-mode (official docs) — "There is no new primitive to learn: a Bot **is** a Hermes profile — isolated config, memory, skills, credentials, and chat history under `~/.hermes/profiles/<name>/`. Bot Mode is a UI over that primitive … No core patches, no background daemons, no extra storage." — **Verified**

2. **Bots CAN talk to each other (DM) — documented, via `message_agent`, fire-and-forget, only from canonical Bot Chats.** — bot-mode page §Bot-to-bot messaging — "every Bot Chat carries the `message_agent` tool: a Bot messages a teammate by calling `message_agent(target=\"researcher\", message=\"…\")` … delivers into the teammate's canonical Bot Chat. Delivery is **fire-and-forget**: the sender gets a _dispatch_ acknowledgement … finishes its turn, and that process's completion notification carries the outcome" and "The tool exists **only** in canonical Bot Chat sessions on Bot-Mode-managed installs; regular chats, group-room member sessions, and CLI sessions never see it." — **Verified**

3. **A Bot CAN dispatch work to another Bot — but only as a message that triggers one turn in the recipient's Bot Chat; there is no queue/claim/ack semantics beyond the reply.** — bot-mode page — "Bots message each other with attribution, and you can hand work off from any chat"; "The sender can type the request: `constraints` (limits on the answer) and `expecting` (what it needs back)"; "Bot-to-bot delivery is per-invocation: the receiving Bot picks the message up when it next runs. Live interrupt of a Bot mid-conversation is future work." — **Verified**

4. **Bot-to-bot exchanges are hop-capped and replies are notify-only by default.** — bot-mode page — "past `gateway.bot_loop_guard.max_hops` (default 4) a further call is refused and nothing is sent … A message a Bot sends back to the Bot that messaged it goes notify-only automatically … The Bot that receives it cannot message that sender back in the same turn." Config: `gateway.bot_loop_guard.max_hops: 4`, `bot_replies_expect_reply: false`. — **Verified**

5. **The headless gate: `message_agent` needs (1) a session titled exactly `Bot Chat` and (2) at least one profile with `ui_meta: { hermes-bots: … }`.** — bot-mode page §What actually makes a chat a Bot Chat — "on a **headless install with no desktop app** … nothing ever writes either marker, so `message_agent` is unreachable even though the docs-level switch is on". Workaround: `hermes -p <bot> chat -c "Bot Chat" --create-if-missing` + `ui_meta: hermes-bots: {}` in `profile.yaml`. — **Verified** (relevant locally: our install is Desktop + gateway, so the markers presumably exist for roster bots; not checked in this lane).

6. **Group chats: bounded rounds, per-member hidden sessions, bounded transcript window, `@user` escalation.** — bot-mode page §Groups — "Your message triggers up to **three serial rounds** of member turns"; "Hard caps (10 messages per send, 3 rounds) keep rooms from spinning"; "Each member's turn carries every room message since its own last turn — up to about 200 messages or 32,000 characters of transcript"; "Bots pull each other in with `@name`, and escalate real judgment calls to you with `@user` — the group row shows a **needs you** badge"; "Each member keeps a hidden per-room session that grows with every turn; when it gets large enough the member starts answering with empty replies" (→ **Compress history** per member). — **Verified**

7. **Gateway-owned group chats survive Desktop close; classic (Desktop-driven / cross-machine) rooms pause when Desktop closes.** — bot-mode page — "Gateway group chats keep running when you close the Desktop … Every other group chat is a _classic group chat_: Desktop runs its rounds, so it pauses while Desktop is closed." — **Verified**

8. **Routines = cron, results land in the Bot's chat.** — bot-mode page §Routines — "Routines are plain Hermes cron jobs namespaced `[bot:<name>] <routine>` — they also show up in `hermes cron list` … Runs land in the Bot's own chat history". — **Verified**

9. **Per-bot state = the profile directory; roster presentation lives in profile metadata (`ui_meta`), sections/pins partly per-Desktop.** — profiles page §Profiles, agents, and bots — "a profile becomes a Bot when Bot Mode stores its roster presentation (title, avatar, section, hidden state) in the profile's metadata and pins its canonical Bot Chat." bot-mode page: "A Bot's chats, sessions, memory, and routines live on the machine that owns the profile." — **Verified**

10. **Docs' claimed use-cases for Bot Mode: a durable team of specialists, routines, deliberation in group chats, @mention handoffs.** — https://hermes-agent.nousresearch.com/docs/getting-started/learning-path — "\"I want a team of specialist Bots\" — Create named Bots with their own model, memory, skills, routines, and chats, then bring them together in group chats or through `@mentions`." Docs landing: "Bot Mode — Build a durable team of specialist Bots that work together in group chats and through @mentions". — **Verified**

11. **One gateway process serves all local Bots; no per-bot backend pool or limit.** — bot-mode page §Local Bots and the gateway — "Desktop does not run a backend per Bot. One gateway process per host owns every local profile's sessions … There is no Desktop-side backend pool, no limit setting for how many Bots can be warm, and no idle reaper". — **Verified**

12. **Cross-machine bot DMs: Desktop is the courier (or `hermes peer` over api_server), with long timeouts.** — bot-mode page — "Cross-connection delivery works while a Desktop that knows both connections is running"; "the Desktop's own delivery deadline (~26 minutes) … The sender keeps waiting long enough … (~52 minutes in all)"; "A relayed message gives the target Bot 10 minutes to finish its turn." `hermes peer dm` "holds one HTTP connection until the turn finishes". — **Verified** (not relevant to single-pod install, noted for completeness)

### (b) Subagent delegation (`delegate_task`)

13. **Subagents are fresh conversations of the same profile; only the final summary returns to the parent.** — https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation — "Subagents start with a **completely fresh conversation**. They have zero knowledge of the parent's conversation history"; "Only the final summary enters the parent's context, keeping token usage efficient"; profiles page: "A separate conversation is different from a separate profile." — **Verified**

14. **Hard limits: no user interaction, no memory writes, no cron, no cross-platform messages; leaf cannot delegate.** — delegation page §Inherited Tool Access — "`clarify` — subagents cannot interact with the user; `memory` — no writes to shared persistent memory; `send_message` — no cross-platform side effects; `cronjob` — no scheduling more work in the parent's name"; "`delegate_task` — blocked for leaf subagents (the default)." — **Verified**

15. **Orchestrator pattern: `role="orchestrator"` + `max_spawn_depth ≥ 2`; orchestrator waits for its batch in-turn; cost multiplies per level.** — delegation page §Depth Limit — "Gated by `delegation.max_spawn_depth` (default **1** = flat, so `role=\"orchestrator\"` is a no-op at defaults)"; "An orchestrator subagent waits for its whole batch in the current turn so it can synthesize the results"; "**Cost warning:** With `max_spawn_depth: 3` and `max_concurrent_children: 3`, the tree can reach 3×3×3 = 27 concurrent leaf agents. Each extra level multiplies spend". — **Verified**

16. **Background results re-enter the parent conversation between turns; parent should end its turn rather than poll.** — delegation page §Batch Mode — "By default the call returns **one** consolidated message once every task has finished. Results are delivered only between the parent's turns: the parent should finish anything that does not depend on the children, then end its turn rather than polling". `independent_completions: true` is off by default because "every unit is a new turn for the orchestrator: a 15-task call becomes up to 15 wake-ups, which fragmented long campaigns." — **Verified**

17. **Lifetime: dies with the owning session / process restart; completions durable, execution not.** — delegation page §Lifetime and Durability — "Background completion durability is not durable execution"; "when the last viewer exits or runs `/new` … the gateway interrupts that session's background children at once"; "A Hermes process restart does **not** resume a running child. Its attempt becomes `unknown`"; "For **durable execution** that must survive session closure or process restart, use: `cronjob` … `terminal(background=True, notify_on_complete=True)`". — **Verified**

18. **Gateway/messaging mode: with interim messages off the chat joins children inline (turn blocks); `/stop` or a follow-up under `busy_input_mode: interrupt` kills children.** — delegation page §Messaging chats without interim messages — "`auto` (default): a messaging chat whose resolved `display.interim_assistant_messages` is off … joins its children inside the turn"; "`/stop` stops the children, and so does a follow-up message under the default `busy_input_mode: interrupt`". — **Verified** (directly relevant to Telegram-attached sessions locally)

19. **Token/cost statements for delegation.** — delegation page — "the children are where the tokens go — a parallel batch of subagents typically burns the large majority of a run's total tokens, so the worker model is where the cost actually lives"; one-shot cap rationale: "each such child re-pays a cold system prompt and re-reads the repo"; compaction cap rationale: "a replay of a 1,393-agent run put 200K–400K caps within 5% of each other in cost once cache prefixes are intact". Delegation vs execute_code table: "Token cost | Higher (full LLM loop) | Lower (only stdout returned)". — **Verified**

20. **Per-child model routing: global `delegation.model`, or `advanced-delegation` plugin (`profile_routes` runs a child *as another profile*, `model_map`).** — delegation page §Delegation strategies — "a **profile per subagent** (`profile_routes`): each child runs as one of your Hermes profiles, with that profile's model, credentials, skills and persona"; default strategy "has no per-task model parameter … hand the task to the kanban board, which does support a per-task model override." — **Verified**

21. **Stall detection replaces wall-clock timeouts (latency semantics).** — delegation page — "By default there is **no wall-clock timeout** on subagents"; stale thresholds "450s idle between turns, 1200s while inside a tool"; opt-in `child_timeout_seconds` bounds "inactivity, not total runtime". — **Verified**

22. **Kanban-worker + delegate_task coexistence: children are reserved under the worker, end with it, and cannot touch the board.** — https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban — "its `delegate_task` children are reserved by that gateway under the worker's execution … returns its result inside the card's turn, and ends with the worker. If the gateway goes down mid-child, the child is retired, never resumed"; "`delegate_task` children do not gain permission to mutate the board." — **Verified**

### (c) spawn_session / child sessions / api_server

23. **`spawn_session` is NOT in official docs; it is a third-party Desktop plugin (Big-Whoop/hermes-spawn-session) with an open core issue asking for public seams.** — https://github.com/Big-Whoop/hermes-spawn-session (README) + https://github.com/NousResearch/hermes-agent/issues/140199 (GitHub issue, labelled P3/type-feature, open) — README: "From the session you are working in (A), it starts a new, visible session (B) with its own model and reasoning effort. B gets a task and context, works on its own, and then **reports back into A**"; "The plugin only works in Desktop sessions"; "**One level only.** B … cannot spawn further sessions"; "At most **3** running agent-started children per parent"; needs `plugins.entries.spawn-session.allow_gateway_injection: true`. Issue: "a planned Desktop plugin, still a work in progress and not released". — **Plausible** (third-party; not an official mechanism)

24. **api_server sessions are isolated from UI/messaging sessions and never auto-run a turn on a delegation completion.** — https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server — "**API sessions are their own sessions.** … they cannot bind a session that another surface owns — a CLI, TUI, Desktop, ACP or messaging conversation. Such a request is refused with HTTP 409"; "A completion **never starts an unsolicited model turn** … The client owns the next turn." Stream carries "`subagent.start` and `subagent.complete` lifecycle events … token/cost figures, a `child_session_id`". — **Verified**

25. **`hermes peer` = bot-to-bot across machines over api_server; the only documented always-on machine-to-machine bot path.** — bot-mode page §Bot-initiated DMs across machines — "`hermes peer dm` delivers into the remote agent's canonical Bot Chat over the peer's existing API server, runs one agent turn there, and prints the reply"; "`peer run` returns a `run_id` immediately; poll it with `peer status`". — **Verified**

### (d) Mixture of Agents and /personality

26. **MoA is a model-level ensemble inside ONE session, not a coordination mechanism; aggregator pays.** — https://hermes-agent.nousresearch.com/docs/user-guide/features/mixture-of-agents — "Mixture of Agents is a virtual model provider"; "The **aggregator is billed for the whole run**: it runs every step of the tool loop"; "Use MoA when a hard task benefits from multiple model perspectives but still needs Hermes' normal agent loop"; cadence: "`fanout: user_turn` … the cheapest cadence: advisor cost does not multiply with the number of tool calls in a turn"; "`fanout: per_iteration` … at the cost of multiplying advisor latency and spend by the number of tool calls". — **Verified**

27. **`/personality` is a per-session system-prompt overlay (persona switch), not an agent/role mechanism.** — https://hermes-agent.nousresearch.com/docs/user-guide/features/personality — "`/personality` is a session-level overlay that changes or supplements the current system prompt"; "`/personality` = temporary mode switch"; FAQ lists it as a WhatsApp workaround: "Use a single profile with personality switching … The agent sees which chat it's in and can adapt." — **Verified**

### (e) Token-cost / latency comparisons between mechanisms

28. **The only side-by-side comparison in the docs is Kanban vs delegate_task (shape, not tokens).** — kanban page §Kanban vs. `delegate_task` — table rows: "Shape | RPC call (fork → join) | Durable message queue + state machine"; "Parent | Blocks until child returns | Fire-and-forget after `create`"; "Child identity | Anonymous subagent | Named profile with persistent memory"; "Human in the loop | Not supported | Comment / unblock at any point"; "Audit trail | Lost on context compression | Durable rows in SQLite forever"; "Coordination | Hierarchical (caller → callee) | Peer — any profile reads/writes any task". No token or latency numbers. — **Verified**

29. **Kanban workers are full OS processes; cost split statement mirrors delegation's.** — kanban page — "every worker is a full OS process with its own identity"; "the workers are where the vast majority of tokens are spent, so the worker model is where the cost lives. Run your orchestrator/dispatcher profile on a frontier model and point worker profiles at inexpensive models." — **Verified**

30. **Per-worker prompt content (skill injection) is described qualitatively, never sized.** — kanban page — "it's injected into the worker's system prompt at spawn (the `KANBAN_GUIDANCE` block)"; "The dispatcher emits one `--skills <name>` flag per skill listed, so the worker spawns with all of them loaded on top of the auto-injected kanban guidance"; orchestrator guidance "is injected into the worker's system prompt automatically". Measurement tool: FAQ "Run `hermes prompt-size` to measure it … the system prompt plus tool schemas sent on every call". — **Verified** (no numbers in docs)

31. **Cron's explicit cost statements are the most concrete in the docs.** — cron page — "carrying `browser`, `delegation` into every tiny 'fetch news' job bloats the tool-schema prompt on every LLM call"; "`wakeAgent` gate gives you a $0 way to decide whether a scheduled job should spend any LLM tokens"; no-agent mode "No tokens, no model, no provider fallback"; bot-chat delivery "Each delivery costs the target bot one full agent turn — mind the schedule frequency"; blocked_config "no LLM call is made — a misconfigured job never spends tokens". — **Verified**

32. **Prompt-cache framing: model switches and `/delegation --now` cost a cache miss; delegation gets a fresh (cold) context.** — FAQ — "Each `/model` switch resets the prompt cache … On long sessions, prefer delegation (subagents get their own fresh context) or a new session"; delegation page: `/delegation <backend> --now` "at the cost of one prompt-cache miss". — **Verified**

33. **Latency numbers that exist: kanban dispatch tick 60 s default (locally 5 s), subagent stale thresholds 450/1200 s, group-chat member turn up to 3 h, bot DM relay 10 min / ~26 min / ~52 min, cron tick 60 s.** — kanban page ("ready tasks get picked up on the next tick (60s by default)"), delegation page, bot-mode page, cron page ("The gateway ticks the scheduler every 60 seconds"). — **Verified** (no end-to-end latency comparison exists)

### (f) FAQ / guidance on profiles vs delegation vs kanban vs cron

34. **Kanban page gives the only explicit "use X when" rule.** — kanban page — "**Use `delegate_task` when** the parent agent needs a short reasoning answer before continuing, no humans involved, result goes back into the parent's context. **Use Kanban when** work crosses agent boundaries, needs to survive restarts, might need human input, might be picked up by a different role, or needs to be discoverable after the fact." Workloads "delegate_task can't": "Research triage — parallel researchers + analyst + writer, human-in-the-loop; Scheduled ops …; Digital twins …; Engineering pipelines — decompose → implement in parallel worktrees → review → iterate → PR; Fleet work". — **Verified**

35. **Profiles: one agent per profile, no shared memory/sessions; shared memory → external provider.** — profiles page + FAQ — "Never point two agent processes at the same profile"; FAQ: "Each profile has its own memory store, session database, and skills directory. They are completely isolated … for genuinely shared memory across agents, use an external memory provider". — **Verified** (matches local Hindsight setup)

36. **Delegation page's own rule of thumb (vs execute_code) and the "agent decides" tip.** — delegation page — "Use `delegate_task` when the subtask requires reasoning, judgment, or multi-step problem solving. Use `execute_code` when you need mechanical data processing"; "The agent handles delegation automatically based on the task complexity." — **Verified**

37. **FAQ multi-model workflow: delegation is the recommended way to route "different task → different model" without switching the main chat.** — FAQ §Using different models for different tasks — "**Solution: Delegation config.** Hermes can route subagents to a different model automatically." — **Verified**

38. **Durable alternatives named by the delegation page are cron and background terminal — not Bot Mode.** — delegation page — "For **durable execution** that must survive session closure or process restart, use: `cronjob` … `terminal(background=True, notify_on_complete=True)`". — **Verified**

## C. What is NOT documented (explicit gaps)

- **No token or latency benchmark comparing Bot Mode, delegate_task, kanban, cron.** Only qualitative statements ("workers burn the majority of tokens", "bloats the tool-schema prompt", "costs one full agent turn") and isolated timeouts/ticks. No "subagent costs X tokens" figure anywhere.
- **No documented system-prompt size per kanban worker, per subagent, or per Bot Chat** (the Bot Chat protocol section + teammate roster is injected at prompt-build time but is never sized). `hermes prompt-size` is the only measurement tool mentioned.
- **No bot-to-bot work queue / task assignment / status tracking.** `message_agent` is a one-turn DM with a reply; there is no claim/ack/retry/board semantics, and the docs explicitly say "Live interrupt of a Bot mid-conversation is future work."
- **No statement that a Bot can create kanban cards for another Bot** via Bot Mode specifically (kanban `kanban_create` from an orchestrator profile is documented, but no Bot-Mode ↔ kanban integration beyond "Open recent session" showing "a delegated job").
- **No official `spawn_session` / child-session primitive.** Only the third-party plugin and an open feature-request issue (#140199) for the plugin seams.
- **No guidance page "profiles vs delegation vs kanban vs cron vs bot mode".** The closest is the kanban-vs-delegate_task table, the learning-path "I want a team of specialist Bots" route (Desktop → Profiles → Bot Mode → Cron → Multi-connection), and the FAQ WhatsApp workaround list (personality / cron / separate numbers).
